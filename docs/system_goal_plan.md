# 시스템 목표와 단계 계획 (S1~S3)

작성 2026-11-25. FFT 가속(E01~E14)은 [단계별 가속 계획](fft128_dma_plan.md)과
[실험 일지](experiment_log.md)에 있다. 이 문서는 그 위의 **시스템 목표**와 다음 단계를 정한다.
각 단계의 실행 과정·실패·해결은 실험 일지에 S ID로 기록한다.

## 1. 왜 목표를 다시 정하는가

- [프로젝트 계획서](FMCW%20레이더%20신호처리%20시스템%20프로젝트%20계획서.pdf)(10-27)의 목표는
  연속 프레임 처리, 검출 정확성, 크기별 PS/PL 파티셔닝, 상시 계측 네 가지다.
- E01~E14는 그중 **같은 프레임 반복의 단일 FFT 지연**만 줄였다. E14 PL 1.657914 ms,
  같은 회차 NEON 3.489441 ms 모두 현재 프레임 간격 12.8 ms(128 chirps × PRP 100 µs) 안이다.
  따라서 128×128에서 FFT 지연을 더 줄여도 계획서 목표 1의 합격 여부는 바뀌지 않는다.
- 계획 수립 시 없었던 것: CFAR·ground truth 비교, 연속 UDP 처리, 드랍·P99·CPU 계측, 크기 스윕.
  이후 S1b/S1c에서 보드 CFAR 비교를 완료했다. 연속 운용·크기 스윕 검증은 S2/S3에 남는다.

## 2. 목표 정의

**11-26 입력 경계 결정:** 시스템 입력 = ADC 모사 고정 스케일 int16 IQ.
ADC의 float→정수 변환은 측정 범위 밖이며 **Hann 창은 시스템 안**에서 적용한다.
기본 ADC profile1은16비트·고정이득 S=1,600,000 codes/unit, 최근접 짝수 반올림·signed16 포화다.
프레임별 최대값 정규화는 사용하지 않는다. PS와 PL은 같은 정수 입력을 받고,
PS int16→double·각 경로의 창/패킹·FFT/DMA·CFAR·출력은 수신 이후 측정에 포함한다.
S1b/S1c/S2a와 S2b run92111~92123은 **float 입력 조건**의 보존 기록이며 ADC 조건으로 재해석하지 않는다.
새 실험은[S2a-int16](../benchmarks/reports/2026-11-26-s2a-int16/README.md)에서 PC/보드 검증을 분리한다.
기본값 하나를 S2b에 사용하고 ADC 비트 수·스케일 스윕은 후속 실험으로 분리한다.
S2a-int16의 PC·Ubuntu/ARM·보드 PS/PL50ms/20 원본 검증은 완료했다.
새 준비 중앙값은 PS0.556071ms/PL2.460540ms이며, 다음 S2b는 진단을 끈12.8ms/200 예비 검사부터 진행한다.
이 진단 결과를10,000프레임 연속 합격으로 해석하지 않는다.
[S2b-int16 12.8ms/200 예비](../benchmarks/reports/2026-11-26-s2b-int16/README.md): PS는 드랍6·P99 71.1ms,
PL은 드랍0이지만 첫 커널 패킷→출력 P99 19.1ms로 둘 다 12.8ms에 불합격했다. 경로별로 주기를 조정해 유효 구간을 찾는다.

**11-26 실시간 기준·송신 결정(사용자):** 12.8ms는 시뮬레이터 획득 주기(128 chirps × PRP100µs)다.
실제 획득에서는 프레임 데이터가 주기 전체에 걸쳐 도착하므로 첫 패킷부터 잰 지연은 정의상 주기를 넘는다.
따라서 S2b 이후 실시간 판정은 **P99(프레임 N 조립 완료 → 프레임 N CSV flush) < 주기**, 즉
"다음 프레임 조립이 끝나기 전에 이전 프레임 출력"으로 한다. 시작점은 수신기 사용자 공간의 마지막 chirp 조립 완료
시각(`complete_ns`)이며 커널 시각이 아니다. 드랍0·오류0·정확도·큐 안정·유효 송신 부하는 계속 필요하고,
첫 커널 패킷→출력 P99는 보조 지표로 보고한다. 송신은 chirp 간격 100µs(PRP)를 절대 시각으로 적용한다. 송신 부하 유효 조건(11-26 사용자 승인, 지터 반영):
chirp 지각 P99 < 10µs(PRP의10%), 프레임 시작 지각 포함 chirp 총 지각 최대 < 주기의10%(12.8ms에서1.28ms),
프레임 시작 지각 < 주기의10%. 프레임 경계 overrun과 100µs 이상 chirp 수는 참고로 보고한다.
초기안(10µs 이상 chirp 하나라도 있으면 무효)은 VM probe에서 짧은 정지까지 걸러 폐기했다.
**11-26 재고정 송신·정지 허용 규칙(사용자 승인, PL 92344 이후):** 10,000프레임에서 VM 정지(최대34ms)가 66프레임에 생겼다.
절대 시각 송신은 정지 뒤 밀린 chirp를 몰아 보냈고, 주기 여유가0.1ms뿐이라 프레임 시작 지각이 최대118ms까지 쌓였다.
그래서 `--schedule reanchor`를 쓴다. 지각이 지터 한도(10µs)를 넘으면 그 실제 송신 시각으로 시간표를 다시 맞추고, 몰아 보내지 않는다.
이후 송신 부하 유효 조건은 다음과 같다.
- chirp 지각 P99 < 10µs
- 송신 측 최소 chirp 간격 ≥ 100µs−10µs, 최소 프레임 간격 ≥ 주기−10µs (간격 압축 없음)
- 정지 프레임(지각 ≥ 주기10%) ≤ 전체의1%

총 지각 최대·정지 길이·재고정 횟수·실효 주기는 보고만 한다. 정지 지점의 드랍은 그대로 불합격이다.
정지는 입력 공백만 만들어 부하를 줄이므로, 실시간 판정은 명목 주기(12.8ms)로 한다. absolute 송신 결과는 그 규칙으로 보존한다.
**11-26 처리 실시간과 네트워크 손실 분리(사용자 결정):** 실제 시스템 입력은 네트워크를 거치지 않는다(ADC→PL).
그래서 UDP 시험 경로의 kernel_drops와 그로 인한 partial/evicted 프레임은 위치와 함께 보고하고, 처리 판정에서는 뺀다.
처리 실시간 합격은 다음을 모두 만족해야 한다.
- 연속 10,000프레임에서 조립완료→출력 P99 < 주기
- queue_full 0
- 송신 유효
- 그 밖의 카운터(clock_errors 포함) 0
- 독립 검산 통과

이전의 "드랍0" 판정은 그 기준의 기록으로 보존한다.
이전 burst/첫 패킷 기준 결과(92311/92312 포함)는 그 조건의 기록으로 보존하고 두 기준을 나란히 표기한다.

**11-26 최상위 목표 변경(사용자):** 실제 획득 간격(PRP)으로 송신하면 프레임 주기는 획득 시간이 하한이므로
고정 입력에서 "최대 프레임률"은 정의되지 않는다. 또 FFT는 PL(약1.4ms)이 PS(약5.3ms, NEON 오프라인3.56ms)보다 빠르다.
따라서 최상위 목표를 **입력 크기를 늘리며 실시간 조건을 만족시키는 것**으로 바꾼다.
PS-only와 PS+PL은 계속 **조건을 나눠 각각 측정**하고 보고하지만, 최대 프레임률 비교·교차점 제시는 주 목표가 아니다.

- **주 목표(11-26~):** UDP 수신(chirp 실제 간격) → 창/FFT → CFAR → 출력 end-to-end 경로에서 입력 크기를 128×128부터 늘려 가며,
  각 크기의 획득 주기에서 실시간 조건(드랍0·오류0·정확도·큐 안정·유효 송신 부하·**조립완료→CSV flush P99 < 주기**)을
  만족하는지 판정하고, 만족하는 가장 큰 크기와 각 크기의 병목·여유를 제시한다. PS-only와 PS+PL은 같은 조건에서 따로 측정한다.
- **이전 주 목표(11-25~11-26, 보존):** 입력 크기별로 드랍 0과 P99 처리 시간 < 프레임 주기를 유지하는 최대 프레임률을
  PS-only와 PS+PL에서 측정하고 교차점을 제시한다.
- **정확성:** 검출한 타겟의 거리·속도 bin이 ground truth의 기대 bin과 ±1 bin 안에서 일치하고,
  오검출 수를 함께 기록한다. FFT bin 수치 일치(기존 검증)는 하위 검사로 유지한다.
- **제약:** Zybo Z7-10(XC7Z010) 자원, PetaLinux soft real-time, 시뮬레이터 입력.
- **보조 지표:** CPU 사용률, 메모리, PL 자원·타이밍, 단일 프레임 지연.

### 자원 사용과 최종 비교 조건 (11-26 사용자 결정)

- 최종 시스템 비교는 Zybo의 두 CPU 코어를 PS-only와 PS+PL 모두 사용할 수 있게 한다.
  `--cpu0` 고정은 단일 코어 진단/기준 실험으로만 보존하며 최종 CPU 최대 처리량으로 쓰지 않는다.
- 첫 변경은 기존 rxfix1 실행 파일에서 `--cpu0`를 제거해 수신과 처리 스레드가 두 코어에서
  병행하도록 허용하는 것이다. 실행 시 online CPU와 상속 affinity가0-1인지 확인한다.
  옵션 제거만으로 두 코어가 항상 포화되거나 FFT/CFAR 자체가 병렬화됐다고 주장하지 않는다.
- 이어서 관측된 병목에 따라 PS의 NEON·FFTW 계획·수신/처리 분리 및 CFAR 병렬화를 검토한다.
  현재 stream PS는 double FFTW ESTIMATE이며, 이전 offline NEON 성능이 통합 경로에 적용된 것은 아니다.
  기존 구현이나 affinity 변경 한 번을 최적 PS의 상한으로 확정하지 않는다.
- 같은 보드·입력/정확성 요구·출력·CPU 코어 사용 한도에서 각 경로의 검증된 최적 구현을 비교한다.
  가속비를 위한 자원 사용률 자체보다 드랍0·P99·정확성을 만족하는 지속 처리량을 우선한다.
  PL은 사용자 선택100MHz를 유지하며 타이밍/정확성 검증 없이 주파수를 올리지 않는다.
- **11-26 스레드 고정 채택(사용자):** S2b-pace 이후 정식 측정은 PS-only와 PS+PL 모두 같은 배치를 쓴다.
  수신 main·sampler 스레드는 CPU0(eth0 IRQ·softirq와 같은 CPU), worker는 CPU1이다. 수신기 바이너리는 바꾸지 않고
  `pin-tid`(`/opt/fft128/pin_tid_20261126_01`, SHA `1a9d19d1…bbd9`)로 실행 직후 고정한다.
  두 CPU를 모두 쓰는 조건은 유지하며 `--cpu0`(전체를 CPU0에 고정)와는 다르다. 이전 미고정 결과는 그 조건의 기록으로 보존한다.
  근거: 미고정 PL에서 반복된 지속 감속(약1.2–1.4배)이 고정한 92339·92340에서 나타나지 않았다(각1회).
  측정 중 보드 셸 반복 기록은 단발 지연을 만들어 사용하지 않는다.
- CPU0 결과와 두 코어 허용 결과는 별도 ID/디렉터리에 보존한다. 송신 주기 불규칙과 시각 오류는
  별도 유효성 조건으로 유지한다. 변경된 CPU 배치로 이 오류들이 해결됐다고 미리 가정하지 않는다.

## 3. 현재 입력의 기대 검출 위치 (계산값, 미검증)

입력: [고정 기록](../benchmarks/fixtures/README.md) 128×128, fs 1.6 MHz, chirp 80 µs, PRP 100 µs,
24.0~24.1 GHz, 표적 30 m / -10 m/s.

| 항목 | 계산 | 값 |
|---|---|---|
| chirp 기울기 | 100 MHz / 80 µs | 1.25e12 Hz/s |
| 거리 분해능 (bin 간격) | c / (2B) | 1.5 m |
| 30 m의 beat 주파수 | 2R·slope / c | 250 kHz |
| Range bin | 250 kHz / (1.6 MHz / 128) | **20** |
| 파장 (24.05 GHz) | c / fc | 12.474 mm |
| Doppler 주파수 | 2v / λ | -1603.4 Hz |
| 속도 분해능 | λ / (2 · 128 · 100 µs) | 0.487 m/s |
| Doppler bin | -1603.4 / 78.125 = -20.52 → 128 - 20.52 | **약 107.5 (107 또는 108)** |

- E11b 기록의 NumPy 피크 (107, 20)와 일치한다. Doppler는 bin 사이(-20.52)에 걸려 있어
  ±1 bin 허용이 필요하다. 부호 규약(-10 m/s ↔ bin 107)은 S1a에서 ground truth로 확정한다.
- S1a에서 고정 기록이 무잡음임을 확인했다. 단일 표적·무잡음 조건이므로 CFAR 오검출 평가에는 다중 표적·잡음 시나리오가 추가로 필요하다.

## 5. 기록 규칙

- 각 S 단계는 실험 일지에 **질문 → 변경 → 검증 경과 → 결과 → 해석 → 다음** 순서로 적고,
  막힌 지점과 해결 과정도 "검증 경과"에 남긴다. 실패한 시도는 지우지 않는다.
- 근거는 `benchmarks/reports/<날짜>-<S ID>/`에 둔다. 증거 종류(PC 시뮬레이션·보드 실측·콘솔·계산값)를 구분한다.
- 위 3절의 기대 bin은 계산값이며 측정이 아니다.
