# FFT128 단계별 가속 계획

상태: **PS01·E11a·E11b 보드 측정·원본 검증 완료. 다음 주 가속 후보는 E13 연산 구조 확대**.
E11b paired 중앙값은 PS double 5.717376 / NEON 3.558177 / PL DMA 6.433026 ms다.
[E11b 측정·정확도·프로파일](../benchmarks/reports/2026-11-19-e11b-board/README.md).
E11a의 5.748489 / 3.715234 / 15.411639 ms는 과거 실행 기준으로 보존한다.
[E11a 측정·원본](../benchmarks/reports/2026-11-16-e11a-board/README.md).
[현재 PS01 근거](../benchmarks/reports/2026-11-15-ps01-board/README.md).
계획 수립일 2026-11-15, PS 목표 갱신일 2026-11-16. [PS01 실행 절차](../benchmarks/ps_precision/README.md).
완료된 [E10 결과](../benchmarks/reports/2026-11-15-pipeline50-benchmark/README.md)와
[실험 일지](experiment_log.md)를 보존하고, 이후에는 한 단계씩 변경·검증한다.

## 기준선과 목표

128 samples × 128 chirps, 동일 Q15 입력·창 없음·전체 1/16384 정규화를 유지한다.
E10 같은 보드 비계측 각 300회 중앙값은 PS double FFTW **5.557368 ms**,
PL pipeline/50 MHz + MMIO **25.2591725 ms**다. 이후 PS01의 각 300회 전체 중앙값은
double **5.502540 ms**, float scalar **4.341573 ms**, float+NEON **3.615852 ms**로 확인됐다.
이후 목표는 NEON 값으로 갱신하고 기존 double 기준도 유지한다. PS01에서 PL을 재측정하지는 않았다.
별도 계측 실행의 평균은 27.327809 ms이고, 그중 입력+출력 MMIO가 20.377574 ms,
PL 내부가 4.408320 ms, PS gather/scatter가 0.946476 ms다.
PL 내부는 시작·대기와 겹치므로 이를 호스트 단계에 더하지 않는다.

목표는 두 가지로 구분한다.

1. 현재 입력의 128 chirps × PRP 100 us에 해당하는 **12.8 ms 프레임 간격**을 감당한다.
   오프라인 지연 외에 연속 입력의 처리량·최악 지연·누락도 별도 검증해야 한다.
2. 같은 조건의 **PS보다 빠른 전체 FFT 경로**를 만든다. 하드웨어 변경 전에 PS01에서
   float+NEON FFTW 기준을 먼저 측정한다. 기존 double FFTW는 이력 비교용으로 유지하고,
   새 PS 기준도 이후 각 단계와 함께 재측정한다. PS Q15는 필요 시 별도 비교로 추가한다.

기존 E10 double 기준에서는 PL 내부 4.408320 ms를 뺀 예산이 약 1.149 ms였지만,
PS01 NEON 목표 3.615852 ms는 PL 내부보다 이미 **0.792468 ms 짧다**.
코어/50 MHz/256회 순차 실행을 유지하는 E11 DMA만으로 PS를 이길 수 있다고 예측하지 않는다.
E11a/b는 전송 고정 비용·묶음 제출을 검증하는 단계로 유지하고, 이후 계산/겹치기 개선이 필요하다.
E10은 클록과 파이프라인을 함께 바꾼 결합 효과다. 프로파일과 사이클 수는 병목 이동을
설명하지만 각각의 독립적인 전체 경로 개선량을 증명하지 않는다.

## PS01 — 하드웨어 변경 전 PS 기준선 강화

FPGA는 E10 그대로 두고, 기존 C++ 경로에 FFTW single+NEON 변형을 별도로 추가한다.
정밀도 변경과 SIMD 효과를 나누려면 double, float scalar, float+NEON을 각각 빌드·실행한다.
FFTW 라이브러리·함수도 `libfftw3f`/`fftwf_*`로 바꾸어야 하며, 현재 double 코드에
`-mfpu=neon`만 주는 것으로 이 비교가 되지 않는다. ARMv7 NEON FFTW는 single 대상으로
구성한다. [FFTW 공식 빌드 설명](https://www.fftw.org/fftw3_doc/Installation-on-Unix.html).

같은 Q15 입력·정규화·32×32 전치·CPU0·단일 스레드·측정 경계를 유지하고,
각 변형의 plan/wisdom을 보드에서 따로 만든다. 계획 생성은 측정 밖이다.
PS float는 PL 정수 모델과 bit-exact를 요구하지 않고 NumPy 기준 최대/RMS/상대 L2 오차,
피크와 PS double 차이를 기록한다. 측정 전에 허용 오차를 정하고 이를 통과한 결과만 비교한다.
처음의 2~3 ms는 사전 가설이었다. 원본 분석 결과 NEON 전체 중앙값은 **3.615852 ms**,
FFT 두 축만의 평균은 1.998061 ms다. 두 구간을 섞지 않는다. 기존 E10 결과나 double 기준은
덮어쓰지 않으며, 이후 PL 단계와 함께 PS도 다시 측정한다.

### PS02 — 전치와 정규화 결합 (별도 계획)

PS01 float+NEON을 보존하고, 별도 변형에서 Doppler 입력 전치에 1/16384 정규화를
결합해 최종 출력 배열을 한 번 더 순회하는 단계를 제거한다. 정밀도·자동 벡터화 정책·
FFTW·plan·입력·CPU affinity를 함께 바꾸지 않는다. 정규화 위치가 달라진 결과는
같은 NumPy 기준으로 매 반복 검증한다. PS01 실행 파일과 측정 결과를 덮어쓰지 않는다.

PS01 NEON 평균 3.622898 ms에서 정규화 0.547702 ms를 단순 제거하면 3.075196 ms다.
이것도 전치 비용·캐시·산술 위치 변화의 효과를 무시한 가설이다. 검토에서 제안한
2.7~3.0 ms는 추가 최적화가 필요한 목표이며 보장값이나 PS의 최저 시간으로 쓰지 않는다.
float 정규화가 double보다 느린 원인은 아직 분리하지 않았고, 결합으로 별도 순회를
없애더라도 그 원인을 설명했다고 주장하지 않는다.

E11b는 먼저 기존 PS01 double/NEON과 같은 실행에서 비교해 제출 단위 변경 효과를 보존한다.
PS02를 추가할 때는 별도 이름으로 비교하고, 이후 최종 PS/PL 비교에는 다시 함께 측정한다.

## 향후 구조와 E11의 고정 조건

```text
PS DDR → AXI DMA MM2S → 스트림 어댑터 → 기존 FFT128 pipeline
       ← AXI DMA S2MM ← 스트림 어댑터 ←
```

DMA의 DDR 접근은 Zynq PS의 HP 경로, 설정·상태는 GP0/AXI4-Lite를 사용하도록 설계한다.
E11은 FFT 코어 하나, 50 MHz, Q15 산술·반올림/포화·출력 순서를 그대로 유지한다.
Range FFT → PS 전치/gather → Doppler FFT의 두 축 처리도 유지한다.
DMA 연결에 필요한 어댑터·제어 로직 변경은 기록하되 연산 코어 변경과 구분한다.

### E11a: DMA로 옮기는 구간과 남는 MMIO

2026-11-16 초기 계획 시점에는 커널 지원 확인·인터페이스 준비 단계였다.
이후 RTL·드라이버·bitstream·보드 측정을 완료했다. 기존 MMIO 구현/펌웨어는 비교용으로 보존한다.

| 구간 | E10 | E11a에서의 역할 |
|---|---|---|
| FFT 입력 128 samples | CPU의 128개 MMIO store | DDR 버퍼를 DMA MM2S로 AXI4-Stream 입력에 전송 |
| FFT 출력 128 samples | CPU의 128개 MMIO load | AXI4-Stream 출력을 DMA S2MM으로 DDR에 저장 |
| FFT 설정·시작·상태·cycle counter | AXI4-Lite MMIO | 제어용 MMIO 유지; 샘플 payload는 통과시키지 않음 |
| DMA 주소·길이·시작·상태 | 없음 | DMA 드라이버가 DMA IP의 MMIO 레지스터를 관리 |
| 두 축 사이 전치/gather | PS | PS에서 유지하며 필요한 버퍼 복사·소유권 전환도 측정 |

따라서 DMA 도입은 MMIO 전체 제거가 아니다. CPU가 샘플마다 수행하던 MMIO를 없애는
것이며 DMA 제어와 완료 처리 비용은 남는다. 사용자 프로그램은 드라이버 인터페이스를
호출하고, DMA 장치용 주소·버퍼·cache 정합성은 커널 DMA API로 관리한다.
각 FFT는 여전히 512-byte 입력/512-byte 출력이며 단일 코어를 순차 실행한다.
묶음 제출·외부 ping-pong·코어 복제·클록 변경은 이 단계에 넣지 않는다.
AXI DMA의 주소·길이·제어 레지스터 동작은
[AMD PG021](https://docs.amd.com/r/en-US/pg021_axi_dma/Direct-Register-Mode-Simple-DMA),
Linux 클라이언트 계약은
[Linux 5.15 DMAengine 문서](https://www.kernel.org/doc/html/v5.15/driver-api/dmaengine/client.html)를 따른다.

복소 샘플은 기존처럼 I 하위 16비트, Q 상위 16비트인 32비트다.
FFT 하나는 512 bytes, 한 축의 128개 FFT는 65,536 bytes다.
중간 결과가 PS DDR로 돌아오는 E11~E13은 두 축 각각 입력·출력이 있으므로
프레임당 전송 payload가 **262,144 bytes (256 KiB)**다. 제어·추가 복사는 별도다.

Linux 쪽은 DMA API를 사용하는 커널 경로로 장치용 주소와 버퍼 소유권을 관리한다.
현재 보드의 커널 설정·사용 가능한 드라이버·일치하는 빌드 소스를 확인한 뒤
DMAengine 클라이언트와 사용자 인터페이스의 구체적인 구성을 확정한다.
일반 사용자 가상 주소를 DMA 주소로 넘기거나 임의의 DDR 영역을 덮는 방식은 쓰지 않는다.
coherent 버퍼인지 streaming mapping인지 명시하고, 전자는 명시적 cache sync가 없다는
사실과 CPU 접근/복사 비용을, 후자는 map/sync 및 소유권 전환 비용을 기록한다.
버퍼 방식 변경도 별도 측정 조건이다. [Linux DMA API 문서](https://docs.kernel.org/core-api/dma-api-howto.html).

2026-11-16 사용자 보드 조회에서 커널은 `5.15.19-xilinx`, `CONFIG_DMA_ENGINE=y`,
`CONFIG_XILINX_DMA=y`, `CONFIG_CMA=y`, `CONFIG_DMA_CMA=y`, `CONFIG_OF_OVERLAY=y`다.
`CONFIG_CMA_SIZE_MBYTES=16`은 설정값이며 실제 부팅 시 예약량·할당 가능량은 별도 확인한다.
DMA 드라이버는 built-in이므로 이를 위해 드라이버 모듈을 먼저 설치할 필요는 없다.
조회 당시 FFT용 DMAengine 클라이언트·버퍼 인터페이스는 없었으며, built-in 지원만으로
새 DMA IP의 Device Tree 등록·IRQ/클록·버퍼 접근이 준비된 것은 아니었다.
보드 `/lib/modules/5.15.19-xilinx/build`가 없어 클라이언트 모듈 빌드 전에 같은 커널의
소스·설정·빌드 산출물을 Ubuntu에서 확보해야 한다. Ubuntu 호스트의 generic 커널 헤더로
보드 모듈을 빌드하지 않는다. 커널 재빌드 필요 여부는 일치하는 빌드 트리 확인 후 결정한다.
위 조회 시점의 준비 항목은 이후 별도 후보 커널 트리와 모듈 CRC 검사로 해소했다.
기존 부팅 커널은 교체하지 않았고, 완료 상태는 E11a 보고서에서 확인한다.

### 캐시·버퍼 정책: 큰 성능 위험과 별도 비교 항목

- **HP + coherent 버퍼:** 이 ARMv7 비일관성 경로에서는 CPU가 접근하는 DMA 매핑이
  non-cacheable일 수 있다. coherent는 항상 CPU 캐시가 켜져 있다는 뜻이 아니다.
  실제 커널·사용자 mmap 속성을 확인한다. DMA 버퍼에서 직접 전치하면 E10의 0.946476 ms를
  유지한다는 가정이 깨질 수 있다. cacheable 작업 버퍼에서 전치하고 복사하는 대안도
  복사 비용을 포함해 비교하며, 이 정책 변경을 같은 결과에 섞지 않는다.
- **HP + streaming mapping:** 입력은 device 소유권, 출력은 CPU 소유권으로 돌려주는
  시점의 map/sync/unmap을 기록한다. 256 KiB는 양방향 payload 합계이며 매번 전부를
  flush와 invalidate 둘 다 한다는 뜻은 아니다. 방향·정렬·cache line·재사용에 따라
  실제 유지보수 범위와 비용이 달라지므로 바이트 수만으로 시간을 정하지 않는다.
- **ACP 비교 (선택, 별도 실험):** HP가 검증된 후 같은 코어·클록·전송 단위로 비교한다.
  coherent 접근에 필요한 AXI 속성, CPU 매핑, Linux 장치의 일관성 설정을 함께 확인한다.
  포트만 옮기거나 DT에 `dma-coherent`만 적는 것으로 일관성이 보장되지는 않는다.
  올바른 coherent 경로는 명시적 캐시 유지보수를 줄일 수 있지만 DMA API의 소유권·순서
  관리는 유지한다. CPU와 캐시/인터커넥트를 공유하므로 경쟁과 캐시 오염도 측정한다.
  [Zynq-7000 TRM: ACP DMA](https://docs.amd.com/r/en-US/ug585-zynq-7000-SoC-TRM/PL-DMA-via-AXI-ACP).

E11a→E11b에서는 버퍼/cache 정책을 고정한다. 버퍼 정책·HP/ACP·IRQ/polling 변경은
각각 구성 이름과 측정 결과를 따로 두어 제출 단위 변경의 효과와 구분한다.

| E12 | 외부 ping-pong 버퍼와 스케줄러로 다음 FFT 전송과 현재 FFT 계산 겹치기 | 단일 코어·50 MHz·Q15 | 겹친 구간의 하드웨어 근거, 프레임 지연과 정상상태 처리량을 각각 측정 |
| E13 | 코어 수 k 확대 또는 스트리밍 FFT 중 하나 선택 | 전송·정밀도·측정 조건 | 연산 및 전체 경로 개선, DDR/포트 경쟁, 자원·타이밍 확인 |
| E14 (선택) | PL 내부 중간 결과 보관과 전치 | 같은 수학적 결과·외부 출력 배열 | PS 전치와 중간 DDR 왕복을 실제로 제거했는지 확인 |

E11a도 단일 FFT 마이크로벤치에서 끝내지 않고 기존 전체 프레임 하네스로 측정한다.
DMA 수신을 준비한 뒤 입력을 보내고, 오류·유한 timeout·reset/재실행을 확인한다.
E11b의 DMA 전송 길이는 65,536 bytes를 표현할 수 있도록 IP 설정에서 검증한다.
선택하는 DMA 모드와 드라이버 지원은 실제 Vivado 2022.1 IP·커널 조합으로 확인한다.
[AXI DMA PG021, 2022-04-27](https://www.amd.com/content/dam/xilinx/support/documents/ip_documentation/axi_dma/v7_1/pg021_axi_dma.pdf).

E11b는 DMA와 별개의 **제출 단위 변경**이다. 현재 코어의 TLAST는 매 128번째 샘플이고,
한 축 묶음의 외부 TLAST는 마지막 16,384번째 샘플이어야 한다.
어댑터가 내부 FFT 경계와 외부 DMA 패킷 경계를 변환하고 개수·오류를 검사한다.
Simple S2MM은 축당 하나의 65,536-byte 패킷을 받도록 구성한다. 코어 출력의 FFT별
TLAST를 외부에 그대로 전달하지 않고 축 마지막에만 assert한다. 반대 방향에서는
MM2S의 축 마지막 TLAST와 코어가 기대하는 FFT별 입력 경계도 구분한다.
길이 필드 17비트의 최대 표현값은 **131,071 bytes**로, 65,536 bytes를 표현할 수 있다.
E11b에서는 coherent bounce·cached 전치·복사 단계 수를 유지한다. 버퍼 크기가
512 B에서 64 KiB로 변하므로 복사 시간이 그대로라고 가정하지 말고 다시 잰다.
프레임당 목표는 **ioctl 2회, DMA 채널 제출 4회(TX/RX 각 2회), FFT 256회**다.
채널당 전송 완료 IRQ 하나라면 330프레임에서 IRQ 증가는 방향별 660회가 기대값이다.
실제 횟수·실제 수신 길이 65,536 B·FFT/샘플 개수·경계 오류를 확인한다.
64 KiB 버퍼·요청 영역은 측정 전에 할당하고 기존 512 B ABI/결과는 별도로 보존한다.
현재 [전체 프레임 인터페이스 초안](interfaces.md)의 가변 크기 지원까지 E11에서 구현하지는 않는다.

E11c는 현재 `fft128_pipeline.v`의 `OUT_REQ` ↔ `OUT_SEND` 교대만 바꾸는 독립 실험이다.
첫 RAM read 지연을 포함한 출력 상태 전환에 따라 FFT당 약 127~128사이클,
256 FFT/50 MHz에서 약 **0.650~0.655 ms** 감소가 무정지 상한이다.
DMA 교체와 동시에 수정하지 않는다. prefetch/보관 레지스터를 설계하고, 임의 길이의
`TREADY=0`에서도 valid/data/TLAST가 유지되며 샘플 누락·중복이 없는지 검증한다.
새 전체 사이클 수는 RTL에서 다시 확인한 뒤 기대값을 확정한다.

현재 FFT 내부 stage 간 ping-pong RAM은 E12의 외부 전송 버퍼와 다르다.
현재 코어는 한 FFT의 LOAD → CALC → OUTPUT을 순서대로 처리하므로 DMA 추가만으로
다음 FFT 로드와 현재 계산이 겹치지 않는다. E12의 겹치기에는 외부 버퍼·포트 설계가 필요하다.
같은 프레임 안의 FFT 벡터 겹치기와 서로 다른 프레임 겹치기도 구분해 기록한다.

E13의 시간은 자동으로 1/k가 되지 않는다. 대역폭·중재·버퍼 포트·전치·자원과 routed
타이밍이 허용하는 k를 선택한다. 스트리밍 FFT로 산술 순서가 달라져 비트 일치가 깨진다면
새 정수 모델·독립 정확도 기준을 정의하고 정밀도 변경을 구조 변경에 숨기지 않는다.
E14도 단순히 PL에서 전치한 뒤 중간 데이터를 다시 PS로 보내면 왕복은 없어지지 않는다.

## 사전 수치 가설과 벗어났을 때의 해석

아래는 측정값이 아니라 **조건부 계산·민감도 가설**이다. 초기 가설은 보존하고 실제값과
차이를 설명한다. 단순 합산 모델은 단계가 겹치지 않는 E11 기준이며 E12부터 바꾼다.

32-bit × 50 MHz = 200 MB/s는 한 방향 스트림의 매 클록 전송 가능한 peak다.
256 KiB / 200 MB/s = **1.310720 ms**는 양방향 payload를 차례로 보낸 등가 전송 시간이다.
독립 MM2S/S2MM가 겹칠 수 있는 구조 전체의 보편적인 하한은 아니다.
현재 코어는 출력 1 sample/2 clocks이며 LOAD/OUTPUT도 내부 861사이클에 포함되므로,
1.310720 ms를 4.408320 ms에 다시 더하지 않는다. 추가 DMA 정지·시작/꼬리 지연은 별도다.

비교용 기준 합 `B = 4.408320 + 0.946476 = 5.354796 ms`를 둔다.
이는 기존 계측값을 쓴 사고 모델로서 새 DMA 경로의 하한이나 보장값은 아니다.
`C`는 추가 복사·cache 관리, `S`는 추가 backpressure·DDR 정지·드라이버 잔여 비용이다.
아래 h/H는 코어 active 구간과 겹치지 않는 노출된 고정 host 비용으로 정의하며,
서로 겹치는 제출·대기 구간을 다시 더하지 않는다. C·S에서도 h/H와 중복되는 비용을 뺀다.
캐시 정책이 바뀌어 전치 시간이 달라지면 0.946476 대신 새 측정값을 넣는다.

| 단계 | 사전 계산/가설 | 벗어날 때 우선 확인 |
|---|---|---|
| PS01 | 사전 가설 2~3 ms → 실측 전체 중앙값 **3.615852 ms**, FFT only 평균 1.998061 ms | 비FFT 평균 약 1.625 ms가 있어 전체 목표는 2~3 ms에 이르지 못함; 기존 가설과 실제값을 구분 |
| E11a | `B + 256h + C + S`. FFT당 두 DMA 방향의 합산 고정 host 비용 h가 20/50/100 us라면 **10.475/18.155/30.955 ms + C + S** | 512개 channel 제출·완료 처리, syscall/IRQ·스케줄링; 느려도 DMA 기능 실패로 판단하지 않음 |
| E11b | 초기 `B + 2H + C + S`의 추가 비용이 0.145~0.645 ms라는 조건에서 **5.5~6 ms**를 가정했다. E11a 복사 실측을 반영한 새 작업 가설은 아래와 같이 **약 8 ms 수준** | 64 KiB 복사 비용, 요청/채널 제출·IRQ 횟수, DMA 정지·경계 처리; 초기 가설을 확정 예상치로 쓰지 않음 |
| E11c | 선행 구성보다 **최대 약 0.65 ms 감소**. 실제 감소는 출력 정지·RAM 제어에 따름 | TREADY 정지, prefetch 기포, 출력이 전체 경로에 가려졌는지 |
| E12 | 벡터 간 LOAD/OUTPUT을 완전히 숨겨도 현 코어의 해당 구간은 `(128+256)×256/50 MHz` = **1.966080 ms**. 이것은 추가 외부 전송량과 다른 항목이며 이상적인 숨김 예산 | 실제 겹침·의존성, 추가 버퍼 복사/제어, 시작/마지막 벡터 비용 |
| E13 | k=2로 내부 4.408320 ms 전체가 이상적으로 반감되면 **2.204160 ms**; E11c 적용 시 새 내부값으로 재계산. 전체 프레임 2배 가속을 뜻하지 않음 | DDR·DMA·출력 포트 경쟁, 전치/제출의 비병렬 부분 |
| E14 | 현재 CPU gather/scatter 약 **0.95 ms**와 중간 DDR 왕복 **128 KiB**가 제거 후보. PL 전치·저장·출력 배열 복원 비용을 차감해야 함 | 중간 결과가 정말 PL에 남는지, BRAM 포트/용량·주소 생성 |

E10의 입력+출력 MMIO는 FFT당 약 **79.600 us**다. E11a의 h=20/50/100 us는
DMAengine의 알려진 실측 비용이 아니라 제출 빈도에 대한 민감도 예시다.
단일 FFT/loopback 진단에서 제출·완료를 재고 전체 프레임 수치와 연결한다.
E11a는 기능·고정 비용을 확인하는 단계라서 E10보다 느려도 유효한 실험이다.

### E11a 실측으로 갱신한 E11b 예산

E11a 계측 평균에서 PL nonstall 4.408320 + stream stall 0.074257 +
사용자/커널 입력·출력 복사 합 2.256989 + gather/scatter 1.002013 = **7.741579 ms**다.
이 합에 새 축당 제출·확인·루프 잔여 비용이 남는다. 약 7.5~8 ms라는 검토 예상은
묶음 복사 비용이 같거나 줄고 고정 비용이 작아지는 경우의 작업 가설이다.
64 KiB 전송의 실제 복사·정지·캐시 동작에 따라 8 ms를 넘을 수 있다.
프로파일의 중첩된 ioctl/wait 전체를 이 예산에 다시 더하지 않는다.

E11a의 ioctl 59.37 us/FFT와 PL active 17.51 us/FFT의 차이 약 41.86 us는
계측 실행의 **비코어 잔여 벽시계 시간**이다. 순수 CPU 실행 시간·IRQ 비용을 직접
측정한 값이 아니다. 특히 wait−active를 IRQ/깨우기 비용으로 확정하지 않는다.
비계측 E11a 15.411639 ms에 계측 복사 합 2.256989 ms를 나눠 정확한 비중으로 쓰지 않는다.
같은 계측 실행 18.136318 ms에서는 복사 합이 약 12.4%다.

E11b가 오프라인 12.8 ms 이내여도 연속 입력의 실시간 처리를 입증한 것은 아니다.
프레임 구분·누락·backlog·정상상태 처리량·최악 지연은 별도 확인한다.
E11b 이후 PS보다 빠르기 위한 코어 예산은 새 PS 전체 시간에서 실제 비코어 비용을
차감해 정한다. 약 2 ms 이하라는 검토값은 그 비용과 PS02 결과에 의존하는 목표다.

### E11b 실제값과 후속 판단 (2026-11-19)

앞선 약8 ms는 작업 가설로 보존한다. 실제 비계측 PL 중앙값6.433026 ms,
PS double5.717376/NEON3.558177 ms이며 각300회 정수/정확도·원본 검증을 통과했다.
별도 계측 평균6.473645 ms 중 PL active4.408947 ms(68.1%), 복사합1.263008 ms,
PS 전치0.670374 ms다. nonstall은 기존4.408320 ms, 외부 stream stall0.000627 ms다.
복사/전치도 과거보다 줄었으며 묶음 크기의 메모리 접근 패턴 변화와 함께 관찰된 결과다.

이 근거로 E13 연산 구조 확대를 주 가속 후보로 둔다. E11c 출력개선의 약0.65 ms 상한은
독립 검증하고, E12에서는 코어 내부 LOAD/OUTPUT을 외부 버퍼로 숨길 수 있는 실제 구간을
설계해야 한다. 외부 stream stall만을 E12의 전체 잠재 이득으로 쓰지 않는다.
복사·전치가 남으므로 코어2개가 전체를2배 빠르게 한다고 예측하지 않는다.
후속 새 소스/측정은 아직 없으며, 다음 변경 전에 구조·예산·검증 범위를 별도로 확정한다.

### E11b 프로파일 후 실행 순서 결정

E12/E13 번호는 변경 종류의 ID이며 실행 순서를 강제하지 않는다. E11c도 독립적으로
측정하고 결과를 기준 구성에 명시한다. 다음 선택은 같은 프로파일에서 판단한다.

- **코어 active 시간이 지배적이면 E13 먼저:** 복제할 수 있는 구간의 예상 절감
  `T_parallelizable × (1 - 1/k)`와 메모리/자원 비용을 계산해 E12의 숨길 수 있는
  시간보다 이득이 큰지 본다. 코어 복제에 필요한 최소 분배 버퍼는 기록하되 ping-pong
  겹치기까지 동시에 넣지 않는다.
- **노출된 LOAD/OUTPUT·외부 전송 정지가 크면 E12 먼저:** handshake/상태 카운터로
  실제 숨길 수 있는 구간을 식별한다. DMA 요청→완료 구간 전체나 내부 4.4 ms 전체를
  숨길 수 있는 시간으로 잡지 않는다.
- **CPU 전치·coherent 버퍼 접근·cache sync가 지배적이면 버퍼 정책부터:** 코어를
  늘리거나 ping-pong을 넣기 전에 원인을 분리하고 별도 구성으로 측정한다.

변경 직전의 관찰·선택 이유·예상 절감·결과를 일지에 남겨 분기 결정을 추적한다.

## 매 단계의 측정 계약

- **주 비교:** 동일 프레임, CPU0, PS01에서 고정한 PS 변형과 기존 double 기준,
  워밍업 10회 후 100회씩 PS/PL 3쌍. 비교 조합별 순서와 결과 디렉터리를 구분한다.
  기존과 같은 300개 원시 표본의 중앙값·평균·p05/p95·최소/최대와 자원·타이밍을 기록한다.
  직전 단계와 PS 두 기준을 모두 비교한다. 새 환경에서는 PS도 함께 다시 측정한다.
  세션 간 PS01→E11a double 중앙값 약 +4.5% 차이의 원인은 미확인이다.
  현재 스크립트는 cpufreq governor/current frequency를 읽을 수 있을 때 저장한다.
  이후 측정에서는 부팅 식별자·IRQ 배치와 주파수 정보의 제공/미제공 여부도 명시한다.
  sysfs 주파수 값은 제공되는 드라이버의 의미를 확인하며 BogoMIPS를 실측 클록으로 쓰지 않는다.
- **시작/끝:** 준비된 동일 Q15 프레임에서, 필요한 DMA 버퍼 복사·소유권 전환을 시작하기
  직전부터 두 축 결과가 CPU에서 읽을 수 있고 기존 결과 배열 순서로 준비될 때까지다.
  제출·완료 처리, 필요한 캐시 관리, PS 전치/gather/scatter, 추가 복사·배열 복원을 포함한다.
  UDP·파일 I/O·일회성 할당·plan/wisdom 생성·입력 양자화·결과 검증은 제외한다.
  한 경로에서 필요한 비용을 측정 밖으로 미리 옮겨 다른 경로와 비교하지 않는다.
- **정확도:** 매 측정 반복 종료 후 타이밍 밖에서 16,384 complex bins를 정수 모델과 비교한다.
  저장 출력은 기존 결과와 비교하고, NumPy 오차·피크도 독립적으로 확인한다.
- **별도 프로파일:** 워밍업 2회/20회. 버퍼 복사, DMA map/sync, 제출, 완료 대기,
  PS 전치, PL 계산 사이클, 외부 TREADY에 의한 정지 및 DMA 전송량을 구분한다.
  DMA 요청부터 완료까지의 호스트 구간은 전송·연산·드라이버 대기를 포함할 수 있으므로
  순수 버스 전송 시간이라고 부르지 않는다. 필요하면 AXIS handshake 카운터로 분리한다.
- **중복:** E12부터 겹친 전송·계산 구간은 합산하지 않는다. 벽시계 전체 시간과 단계별
  구간·겹침을 함께 제시한다. PL 사이클 레지스터 의미가 달라지면 함께 버전 관리한다.
- **연속 운용:** 오프라인 비교와 별도 실험으로 정상상태 frame/s, 프레임별 지연, backlog,
  누락/오류를 측정한다. 현재 UDP에는 frame ID가 없으므로 연속 송신 전 프레임 구분도 해결한다.

각 단계의 결과는 새 디렉터리에 저장하고 입력·소스·비트스트림·실행 파일 해시,
버퍼/cache 정책·DMA 설정·코어 수·실제 제약 클록·setup/hold·자원량을 함께 보존한다.
실패하면 해당 단계에서 원인을 찾고 다음 기능을 더하지 않는다. 기록은 처리·성능에 영향을
주는 변경과 근거 중심으로 남기며, 단순 실행 환경 수정은 실험으로 만들지 않는다.
