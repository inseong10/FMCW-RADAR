# S3a 크기 확장 설계안 (2026-11-26, 제안 · 사용자 결정 대기)

목표([system_goal_plan](system_goal_plan.md)): 입력 크기를 128×128에서 늘려 가며 각 크기의 획득 주기에서 **처리 실시간 조건**을 판정한다.
PS-only와 PS+PL은 따로 측정한다. 처리 실시간 조건은 다음을 모두 만족하는 것이다.
- 연속 10,000프레임에서 조립완료→출력 P99 < 주기
- queue_full 0
- 송신 유효
- kernel_drops 외 카운터 0
- 독립 검산 통과

네트워크 손실은 보고만 한다(11-26 결정).

## 1. 출발점 (128×128 실측, 10,000프레임)

| 경로 | 단계 중앙값 (ms) | 합계 | 주기 12.8ms 대비 | 판정 |
|---|---|---|---|---|
| PS+PL (92348) | prepare 2.54 · E14 FFT 1.55 · CFAR 6.54 · flush 0.22 | ≈10.9 | 85% | 충족 (P99 11.10) |
| PS-only (92352) | prepare 0.63 · FFTW 5.93 · CFAR 5.58 · flush 0.23 | ≈12.4 | 97% | 불합격 (P99 23.8, 참고) |

- **PS+PL 경로의 병목은 FFT가 아니라 PS 쪽 prepare와 CFAR다.** 둘이 합계의 약 83%를 차지한다.
  - 이 두 단계는 셀 수(M·N)에 비례한다.
  - CFAR는 이미 prefix-sum(셀당 O(1))이지만 double·검사·modulo 때문에 셀당 약 0.40µs가 든다.
  - prepare(PL 경로의 Q15 창·패킹)는 셀당 약 0.155µs다.
- PS-only는 128×128에서 이미 여유가 없다. 더 큰 크기는 현재 구현으로 충족할 수 없다고 예상한다(측정은 한다).

## 2. 크기 축과 주기 규칙 (제안)

PRP 100µs와 chirp 80µs·대역 100MHz는 고정한다(실제 레이더의 획득 시간 규칙을 유지).

| 축 | 바뀌는 것 | 주기 | fs | 패킷 (UDP payload) | 의미 |
|---|---|---|---|---|---|
| **D축: chirp 수 M** (128→256→512) | Doppler 분해능 향상 | **M × 100µs** (12.8 / 25.6 / 51.2ms) | 1.6MHz 고정 | 568B 그대로, 패킷 수 M개 | 주기도 같이 늘어난다. 셀당 처리 시간이 같으면 부하율이 거의 일정하다 |
| **R축: 샘플 수 N** (128→256→512) | 최대 거리 ×2 (분해능은 같음) | 12.8ms 고정 | N/80µs (3.2 / 6.4MHz) | 56+4N: N=256은 1080B, **N=512는 2104B로 MTU 초과** | 주기는 그대로이고 일이 N에 비례해 는다. 가장 어려운 축이다 |
| 정사각 N=M (256×256) | 둘 다 | 25.6ms | 3.2MHz | 1080B × 256 | 비교용 대표점 |

- **권장 순서:** D축 128×256 → R축 256×128 → 256×256 순으로 진행한다. N=512(MTU 초과, 패킷 분할 필요)는 마지막이나 별도 단계에 둔다.
- 표적 시나리오(multi4+noise)는 크기마다 radarsimpy로 다시 생성한다. 표적이 각 크기의 거리·속도 범위 안에 들도록 기대 bin을 계산하고, NumPy 기준 모델로 4/4·오검출 0을 먼저 확인한다.

## 3. 현재 구현으로 단순 확장했을 때의 예측 (계산값, 미측정)

128×128 셀당 단계 비용을 그대로 늘린 계산이다. E14는 1회 1.42ms로 둔다.

| 크기 (주기) | PS+PL 예측 합계 | 주기 대비 | PS-only 예측 |
|---|---|---|---|
| 128×256 (25.6ms) | prep 5.1 + FFT 2×1.42+결합≈1 + CFAR 13.1 + flush 0.4 ≈ **22.4ms** | 88% | ≈ 25+ms (불합격 예상) |
| 256×128 (12.8ms) | 같은 셀 수 ≈ 22.4ms | **175%** | 불합격 |
| 256×256 (25.6ms) | prep 10.2 + FFT 4×1.42+결합≈2 + CFAR 26.2 + flush 0.9 ≈ **45ms** | **176%** | 불합격 |

- 결론(예측): **CFAR·prepare를 줄이지 않으면 PS+PL도 D축 한 단계(128×256)에서 여유가 12%뿐이다.** R축과 정사각은 불합격이다.
- 그래서 크기 스윕 전에 **S3a-0: PS 쪽 셀당 비용 감축**을 둔다. 예측표는 실측으로 바꾸고 계산값 표시를 유지한다.

## 4. PL에서 128보다 큰 FFT를 하는 방법 (RTL 변경 여부)

E14는 128×128 2D 고정이다(ABI8 요청 131,280B, 여러 곳에 128 고정).

| 방법 | 내용 | RTL 변경 | 비용 |
|---|---|---|---|
| **A. 분할 (권장 첫 단계)** | 시간 축 decimation이다. 256점 = 짝·홀 128점 둘 + radix-2 결합.<br>예: M=256이면 짝·홀 chirp로 나눈 128×128 프레임 2개를 E14로 각각 처리하고, PS가 Doppler 축에서 `X[k]=E[k]+W^k·O[k]`, `X[k+128]=E[k]−W^k·O[k]`로 결합한다.<br>N=256도 같은 방식이고, 256×256은 E14 4회 + 두 축 결합이다. | **없음** (E14·드라이버 그대로) | E14 호출이 늘고, 결합이 셀당 1회 복소곱이다. Q15 스케일·포화 영향을 검증해야 한다 |
| B. 크기 파라미터화 RTL (S3b) | 256/512점 FFT와 전치를 DDR 기반으로 구현한다(E15-memory). XC7Z010 BRAM 270KB로는 256×256×4B(256KB) 전치가 빠듯하다 | 큼 | 자원·타이밍 검증, 새 드라이버 |

A는 정확도 검증(정수 모델 일치)만 통과하면 RTL 없이 PS+PL 크기 확장을 측정할 수 있다. B는 A의 결과로 필요성이 확인되면 S3b에서 한다.

## 5. 바꿔야 하는 코드 (모두 결정 후 진행)

| 대상 | 현재 | 변경 |
|---|---|---|
| 수신기 프로토콜·조립 (`stream_protocol.hpp`) | 128 고정(패킷 568B, 16384 버퍼) | 헤더의 pulses/samples(M, N)를 실행 인자로 받아 검사한다. 기존 128 동작과 바이트 단위로 같게 한다 |
| 파이프라인 (`stream_pipeline.hpp`) | 배열 16384·창 128·FFTW 128×128 | 크기 인자화. PS는 FFTW M×N, PL은 방법 A(분할+결합) |
| CFAR (`cfar_ca.hpp`) | 이미 크기 인자 지원 | S3a-0에서 셀당 비용 감축. float/NEON, modulo 제거, 두 단계 분리 등 후보 중 측정으로 고르고, 검출 목록이 기준 모델과 같아야 한다 |
| 송신기 `replay_stream.py` / 기록 형식 | 128 고정 | M·N 일반화(N≤256은 1패킷/chirp) |
| 고정 입력 | 128×128 4종 | 크기별 multi4+noise 생성, 기대 bin 계산 |
| 검산기 | 128 기준 | 크기 인자 |

모든 변경은 128×128에서 기존 결과(검출·수치)와 일치하는지 먼저 확인한다. 회귀 기준은 92348이다.

## 6. 단계안

| ID | 질문 | 합격 |
|---|---|---|
| S3a-0 | PS 쪽 prepare·CFAR 셀당 비용을 얼마나 줄일 수 있나 (128×128) | 검출·수치가 기존과 같고, 128×128 10,000프레임 처리 실시간 유지, 셀당 비용 측정 |
| S3a-1 | 크기 일반화가 128×128을 바꾸지 않나 | 128×128에서 92348과 같은 검출, P99 차이 기록 |
| S3a-2 | D축 128×256 (25.6ms) PS+PL / PS-only | 처리 실시간 판정 |
| S3a-3 | R축 256×128 (12.8ms) | 처리 실시간 판정 |
| S3a-4 | 256×256 (25.6ms) | 처리 실시간 판정, 필요하면 S3b 착수 근거 |

각 크기는 200프레임 예비 후 10,000프레임 본검사를 한다. 스레드 고정, reanchor 송신, 에이전트 실행 경로는 128×128과 같다.

### S3a-0 결과 (11-26, 측정)

- 보드 마이크로벤치: prepare 0.132→0.063µs/셀, detect(전력+CFAR) 0.364→0.131µs/셀. 합계 **0.194µs/셀**로 목표를 충족했다. 결과는 비트 동일이다.
- PL 10k: 92357이 처리 실시간을 충족했다(P99 5.527ms). 단계 중앙은 prepare 1.20 · FFT 1.45 · CFAR 2.38 · flush 0.22 = 5.27ms다.
- PS-only 10k: 92358이 충족했다(P99 11.451ms, 처리 11.10ms로 주기의 87%). §1의 "PS-only 128×128 불합격"은 92352 기준이다.
- §3 예측표를 새 셀당 비용으로 다시 계산하면(계산값, 미측정):
  - 256×256 PS+PL ≈ prep 4.8 + FFT 4×1.42+결합≈2 + CFAR 9.5 + flush 0.9 ≈ **23ms**로, 주기 25.6ms의 90%다.
  - 256×128(12.8ms) ≈ 11.6ms로 91%다.
  - 결합 비용(복소곱)은 아직 측정하지 않았다.

### S3a-1 결과 (11-26, 측정)

- 수신·파이프라인·송신·레코드·검산을 크기 인자로 바꿨다. PL·model 정수 경로는 방법 A(블록별 E14/model 128×128 + 비트 역순 배치 + 나머지 DIT 단)를 쓴다.
- 128×128 덤프는 S3a-0과 SHA가 같다(host·보드).
- 10k 처리 실시간도 유지됐다: PL 92404 P99 5.449ms, PS-only 92406 P99 11.635ms.
- 큰 크기는 host 루프백만 했다. 이 문서 표기로 128×256·256×128·256×256·128×512에서 model/ps 4/4였고, model 전bin이 독립 NumPy 기준과 정확히 같았다.
- 보드 PL 분할 경로와 큰 크기 처리 시간은 아직 측정하지 않았다(래퍼가 `--pulses/--samples`를 넘기도록 바꿔야 한다).
- 결합 단계 비용은 미측정이다. [S3a-1](experiment_log.md#s3a-1--프레임-크기-일반화-mn)

### S3a-2 결과 (11-26, 측정)

- 이 문서 표기 128×256(M=256, 25.6ms)에서 결과는 다음과 같다.
  - **PS+PL 10k 92415:** 충족. P99 17.558ms(69%). 단계 중앙: prep 2.26 · FFT 9.95 · CFAR 4.71 · flush 0.23ms.

## 7. 사용자 결정 항목

1. 크기 축과 순서: D축 → R축 → 정사각을 제안한다. N=512는 보류.
2. 주기 규칙: 주기 = M × 100µs, fs = N / 80µs를 제안한다.
3. PL 방법: A(분할·결합, RTL 없음)를 먼저 한다. B(RTL)는 필요가 확인된 뒤에 한다.
4. S3a-0(CFAR·prepare 최적화) 선행 여부. 처리 로직 변경이라 승인이 필요하다.
5. PS-only 최적화(NEON/float FFT)는 범위 밖으로 둔다. 현재 구현 그대로 측정만 하는 것을 제안한다.
