## Probe 92330 — 수신기 없이 VM 송신만 측정

증거: 사용자 Ubuntu 콘솔과, 공유 폴더에서 회수한 [`sender_probe_01.json`](sender_probe_01.json).
`--chirp-detail` 옵션으로 chirp 25,600개 모두의 지각이 들어 있다.
송신기 SHA는 `f3806e43…0a37`이고 Ubuntu `sha256sum` 결과와 같다. Ubuntu에서 `test_check_pacing` 10개가 통과했다.
목적지는 10.0.0.3:5000이었고 보드에서 수신기는 실행하지 않았다. 따라서 이 결과는 송신 측 시각만 보여 준다.
실제 선로에서의 패킷 간격이나 보드 도착 간격은 알 수 없다.

| 항목 | 값 |
|---|---|
| 조건 | 12.8ms, 200프레임, chirp 간격 100µs, spin, 한도 10µs |
| chirp 지각 중앙값 / P90 / P99 / P99.9 / 최대 | 0.141 / 0.233 / 4.141 / 160.8 / 713.3µs |
| 한도(10µs) 이상인 chirp | 151 / 25,600개, 해당 프레임 58 / 200개 |
| 지연 사건(연속으로 늦은 chirp 묶음) | 111건. 최대 지각 10~20µs 49건, 20~50µs 48건, 50~100µs 6건, 100µs 이상 8건 |
| 100µs 이상 사건 (프레임, 시작 chirp, chirp 수, 최대) | (1,0,6,204) (25,120,3,115) (46,0,10,713) (56,5,10,632) (76,115,5,305) (83,127,1,135) (134,15,7,530) (197,91,2,117)µs |

해석:
- chirp의 99%는 4.1µs 이내에 송신됐다.
- 가끔 수십µs에서 최대 0.71ms까지 송신이 멈춘다. 멈춘 뒤에는 송신 시각을 절대 시각으로 정했기 때문에 다음 몇 개 chirp가 연달아 늦게 나가다가 따라잡는다.
- `sendto` 한 번이 0.62ms 걸린 경우가 있다. vCPU 선점과 커널/가상 NIC 지연 중 무엇이 원인인지는 확인하지 않았다.
- 현재 10µs 한도로는 송신 부하가 무효이므로, 이 조건으로는 보드 예비 검사를 진행하지 않는다.

## Probe 92335 — 송신 프로세스 CPU3 고정 + 실시간 우선순위(SCHED_FIFO 50)

증거: 사용자 콘솔과 회수한 [`sender_probe_02.json`](sender_probe_02.json)(SHA256 `384c6687…5ca`), 송신기 SHA `f3806e43…0a37`.
실행 명령: `sudo chrt -f 50 taskset -c 3 python3 tools/sender/replay_stream.py …`. 나머지 인자는 probe 92330과 같다.

| 항목 | probe 92330 (기본) | probe 92335 (고정+FIFO) |
|---|---|---|
| chirp 지각 중앙 / P99 / P99.9 / 최대 | 0.14 / 4.14 / 161 / 713µs | 0.14 / 4.69 / 35,709 / **36,943µs** |
| 10µs 이상 chirp (프레임) | 151 (58) | 173 (40) |
| 1ms 이상 chirp (프레임) | 0 (0) | 86 (1) |
| 프레임 시작 지각 최대 | 0.063ms | **31.92ms** |
| overrun | 1 | **66** |

probe 92335에서는 프레임 135에서 한 번에 36.9ms가 멈췄다. 그 뒤 프레임 136~200(65개)은 절대 시각을 따라잡느라
늦게 시작해 주기보다 빠르게 연달아 송신됐고, 프레임 135를 포함해 overrun 66건이 됐다.
spin으로 CPU를 계속 쓰는 SCHED_FIFO 프로세스가 Linux RT throttling에 걸렸을 가능성이 있지만 확인하지 않은 **가설**이다.
이 설정은 송신 부하를 더 크게 왜곡하므로 앞으로 쓰지 않는다. 이 정지를 빼면 P99(4.69µs)는 기본 설정과 비슷하다.

판정:
- 두 실행 모두 송신 부하가 무효이므로 합격·불합격을 판정하는 데 쓰지 않는다.
- 같은 VM에서 수신기 없이 돌린 probe 92330은 유효했지만 이번 두 실행은 무효였다. 송신 지터가 실행마다 달라진다.

관찰 (부하가 무효이므로 참고용):
- **chirp 간격 송신이 실제로 반영됐다.** 첫 패킷→조립완료가 약 12.87ms로, burst 송신 때의 4.75ms와 다르다.
  VM이 패킷을 크게 묶어 보냈다면 이 값이 짧아졌을 것이므로, 그런 묶음은 없었다고 간접 확인된다.
- **PS는 처리 시간 자체가 주기를 넘는다.** 처리 합계 중앙값이 약 16.9ms다.
  FFT는 8.09ms로 burst 6.16ms·진단 5.26ms보다 길고, CFAR는 7.59ms로 burst 5.08ms보다 길다.
  패킷이 주기 내내 들어오면서 수신 처리와 IRQ가 CPU를 나눠 쓴다는 **가설**이며, 확인하지 않았다.
  송신 지연은 한 프레임 안 chirp 사이의 일이므로, 이것만으로 이렇게 처리 시간이 긴 것을 설명하기는 어렵다.
- **PL의 정상 구간은 새 기준을 만족하는 수준이다.** 프레임 1~15와 84~200의 조립완료→출력 중앙값은 10.75 / 10.84ms다.
  이 구간의 CFAR 6.45~6.49ms는 burst 송신 때의 8.37ms보다 짧다.
- **PL은 프레임 16~83에서 연속으로 느려졌다.** prepare가 2.52→3.11ms, CFAR가 6.45→7.99ms로 둘 다 약 24% 늘었고,
  FFT/DMA는 1.40→1.48ms로 거의 그대로였다. 처리 합계가 주기를 넘자 큐 대기가 최대 7.96ms까지 쌓였다가 프레임 84 이후 회복했다.
  조립완료→출력이 12.8ms 이상인 프레임 66개가 모두 이 구간에 있다.
  송신 정지 프레임(41, 51, 122, 129, 178~198)과는 일치하지 않고, 이 구간에서 시스템 CPU에서 수신기 몫을 뺀 부하도 다른 구간보다 크지 않았다.
  원인(CPU 측 일시 감속, 메모리 경합 등)은 **확인하지 못했다.**

## 진단 PL 92337 — 스레드별 CPU 기록 (진단 전용)

증거:
- 공유 `build/s2a_int16_board_pace3_20261126_adc01`에서 회수했고, Windows 사본과 `diff -r` 기준으로 같다.
- 수신기 SHA는 `72396cb0…28f0`이다. clock 전후 기록은 같다.
- 송신 JSON SHA256은 `5eae784d…a1c2`다.
- 사용자가 보드 셸 반복 명령으로 약 0.19초마다 기록한 `/proc/PID/task/*/stat`(tid, utime, stime, processor)과 cpu0/cpu1 `/proc/stat`은
  [`pl_pace_prelim_03_threads.txt`](pl_pace_prelim_03_threads.txt)(SHA256 `167f24e4…d954`)에 있다.
- 프레임과 맞춘 결과는 [`pl_pace_prelim_03_thread_alignment.json`](pl_pace_prelim_03_thread_alignment.json)에 있다.
- 스레드 구분: 소스 생성 순서상 tid 1171은 main(수신), 1177은 sampler, 1178은 worker다.

판정:
- **trace 무효.** `clock_errors=1`(REALTIME−MONOTONIC 오프셋이 한 번 2ms를 넘음)이라 checker가 거절했다. 원인은 확인하지 않았다.
- **송신 부하 무효.** 지터 P99가 14.92µs다(총 지각 최대 0.644ms).
- 처리는 178/200이다(queue_full 22).
- 보드 셸 기록 반복 명령 자체가 CPU를 쓰므로 이 실행은 성능 판정에 쓰지 않는다.

- 가설을 **부분적으로 뒷받침**하지만 확정하지는 못한다. processor 필드는 샘플 순간의 값이고, 구간 수도 적고, 혼합 구간이 많다.
- 스레드 CPU를 직접 고정해 비교하는 실험이 필요하다.

## PL 92338 — 고정 시도 실패, 고정 없는 반복 실행으로 분류

증거:

## 진단 설계 S2b-diag-out — 출력 위치(NFS vs 보드 RAM) A/B (사용자 승인 11-26, 미실행)

**질문:** 92344·92348의 kernel_drops(소켓 rcvbuf 넘침)와 보드 단발 지연·VM 송신 정지가, 보드 출력을 NFS로 쓰는 데서 생기는가?

**근거(관찰):**
- 보드 rootfs와 출력 디렉터리가 모두 NFSv3/TCP이고, rsize·wsize는 4096이다.
- NFS 서버가 송신기와 같은 Ubuntu VM이고, NFS 트래픽은 UDP 스트림과 같은 eth0를 쓴다.
- 보드 `/proc/net/snmp`의 Udp RcvbufErrors는 누적 4398로 kernel_drops와 같은 종류다.
  eth0 rx drop/fifo는 0이므로 NIC 단계 손실은 아니다.
- 단발 지연 프레임에서 flush가 10~16ms로 늘었고(4904·7258·8437), 같은 때 CPU0 수신 스레드도 늦어졌다(4905 조립 29.4ms).
  - rcvbuf 360448B는 568B 패킷 기준 대략 150개 안팎이다(skb truesize 가정).
  - 패킷이 10개/ms로 도착하므로, 수신 스레드가 15ms 정도 비우지 못하면 넘친다.

**변경하는 것은 하나뿐:** 수신기 출력 디렉터리 위치.
- `ram`: 보드 tmpfs `/var/volatile`(502MiB)에 쓰고, 수신기가 끝난 뒤 NFS 번들로 복사한다. 복사본은 SHA로 대조한다.
- `nfs`: 지금까지처럼 NFS에 쓴다.
- 나머지는 92348과 같다: 수신기·송신기·번들, reanchor 송신, 12.8ms/10,000, queue4/partial4, rcvbuf 360448, 고정 1/1/2, READY·고정 확인 뒤 송신.
- 수신기·드라이버·처리 로직은 바꾸지 않는다.

**순서(시간 변화 통제를 위해 교차):** 92349 ram → 92350 nfs → 92351 ram. 92348(nfs)은 참고 기준이다.

**기록:**
- 래퍼 v2 `tools/agent/run_pinned2.sh`(SHA `2b06ecfd…`)가 실행 직전과 직후에 한 번씩 스냅숏을 남긴다.
  내용은 보드 Udp/eth0/NFS client rpc/cpu/vmstat dirty다. 측정 중 반복 기록은 없다.
- Ubuntu nfsd io와 cpu도 에이전트가 실행 전후 1회 기록한다.
- 판정 지표: kernel_drops와 Udp RcvbufErrors 증가분(같아야 함), flush>4ms 프레임 수, CFAR>8ms 프레임 수, 송신 정지 프레임 수, NFS rpc 호출 증가분, 조립완료→출력 P99.

**해석 규칙(미리 고정):**
- ram 두 번 모두 드랍0이고 nfs가 드랍>0이면 "NFS 출력이 드랍에 기여한다는 가설과 맞음"으로 기록한다. 세 번이라 증명은 아니다.
- ram에서도 드랍>0이면 NFS 출력이 단독 원인은 아니다. 다음 진단은 선로 도착 기록(Ubuntu `tcpdump`, Windows `pktmon`)이다.
- 정지가 드물어(실행당 1~4회) 한 번의 0은 우연일 수 있다. 결과 수치는 실행별로 그대로 나열한다.
- ram 출력을 정식 조건으로 채택할지는 사용자가 결정한다. 이 진단 결과로 12.8ms 합격을 주장하지 않는다.
